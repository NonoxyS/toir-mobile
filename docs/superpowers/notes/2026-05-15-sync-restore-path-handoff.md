# Хэндофф: путь восстановления данных синхронизации

Дата: 2026-05-15
Контекст: разбор надёжности синхронизации в рамках ВКР (ru.mirea.toir).

## С чего началось

Чинили краш `IllegalStateException: Inspection not found:` (пустой `inspectionId`).
По ходу всплыл вопрос пользователя: «Нам важно не терять данные — система сейчас надёжна?»

## Что проверено по коду (факты, не догадки)

**Путь записи на сервер РАБОТАЕТ — как описано в ВКР §1.3.1.**

1. Каждое значение чек-листа / результат точки / обход сохраняются в локальную БД
   сразу со статусом `sync_status = 'pending'`.
   Подтверждение: `Inspection.sq:14`, `ChecklistItemResult.sq:15`, ВКР §1.1.3.

2. Push (`SyncRepositoryImpl.pushPendingData`, строки 75-79) выбирает записи
   **только по `sync_status = 'pending'`** через `selectPendingReady`.
   Фильтра по статусу обхода НЕТ → незавершённые обходы и их результаты
   уходят на сервер наравне с завершёнными.

3. Триггеры синхронизации (`SyncTrigger.kt`, `SyncManager.kt`):
   - Connectivity — авто при возврате сети (`SyncManager.kt:46-54`)
   - Periodic — каждые 2 часа, Android WorkManager (`SyncScheduler.kt:19-22`)
   - Manual, AfterInspection, Bootstrap

**Важно — про прошлую ошибку:** SQL-запрос `selectPendingInspections` в `Inspection.sq`
ДЕЙСТВИТЕЛЬНО фильтрует `status IN ('completed','partially_completed','cancelled')`,
НО он используется только для экранного индикатора (`observePendingInspections()`),
НЕ для push. Метод хранилища `selectPendingInspections(now)` внутри вызывает
другой запрос — `selectPendingReady` (`InspectionStorageImpl.kt:74-75`).
Совпадение имён → ранее был сделан ложный вывод «данные не пушатся». Это неверно.

## Где реальная дыра — ОБРАТНЫЙ путь (восстановление)

`RemoteBootstrapResponse` и `RemoteConfigChangesResponse` содержат только
конфигурацию: assignments, routes, routePoints, equipment, locations,
checklists, checklistItems. **inspections / equipment_results /
checklist_item_results там НЕТ** (оба файла прочитаны целиком).

Следствие:
- Сервер ПОЛУЧАЕТ незавершённую работу (push доставил).
- Но при потере локальной БД (переустановка, очистка данных, новое/сломанное
  устройство) приложение НЕ может вытащить эти данные обратно — нет поля в API.
- Данные не уничтожены — они на сервере, но мобильному приложению недоступны.

Это и есть сценарий `SYNC_REQUIRED`, под который вчера сделана кнопка «Обновить».
**Кнопка в текущем виде восстановить данные не может** — delta не несёт inspections.

## Оценка надёжности

| Сценарий | Статус |
|---|---|
| Креш / закрытие приложения / перезагрузка посреди обхода | OK — локальная БД на месте |
| Пропала сеть посреди обхода | OK — pending, уйдёт при возврате сети |
| Обычная работа, одно устройство | OK |
| Потеря локальной БД посреди обхода (переустановка / новое устройство) | Незавершённая часть не вернётся в приложение |

## Предлагаемое решение

Достроить обратный путь: добавить в ответ `bootstrap` (и/или delta) незавершённые
обходы пользователя с результатами, применять локально в `ConfigChangesApplier` /
при бутстрапе.

- Бэкенд: в `buildBootstrap` отдавать незавершённые inspections юзера +
  equipment_results + checklist_item_results.
- Клиент: расширить `RemoteBootstrapResponse`, писать в локальную БД при
  бутстрапе со `sync_status = 'synced'`.
- Результат: `SYNC_REQUIRED` сам исчезает после загрузки; переустановка
  восстанавливает обход; offline-first замыкается в обе стороны.
